# コーディングガイドライン

このドキュメントは、プロジェクト全体で共通して適用する実装上のガイドラインを定める。

一般的なコーディング作法を網羅することではなく、
このプロジェクトで特に重視する実装方針を明示することを目的とする。

# 全般

- コードの意図は、可能な限り命名・関数分割・型・データ構造によって表現する。
- 変更前に、関連する既存コード・抽象化・命名・設計を確認する。
- 既存のコードスタイル、命名規則、設計方針を尊重する。
- 既存の仕組みで十分表現できる場合、新しい型・utility・abstractionを追加しない。
- 関係のないリファクタリングを行わない。
- 将来必要になるかもしれないという理由だけで抽象化や拡張ポイントを追加しない。
- タスク達成に必要な範囲で、理解しやすく一貫した変更を行う。

# 関数

- 1つの関数には明確な責務を持たせる。
- 意味のある処理単位は名前付き関数やメソッドへ切り出す。
- 長い処理をコメントで区切って説明するより、責務ごとに処理を分割することを優先する。
- 単に行数を減らすためだけの関数分割は行わない。
- 関数へ切り出すことで意図や責務が明確になる場合に分割する。
- 過度に細かい関数分割によって処理の流れを追いにくくしない。

# 公開APIと観察可能な振る舞い

公開APIは、
クライアントから観察可能な振る舞いを表す境界として設計する。

原則として、

**観察可能な振る舞いと公開APIの範囲を一致させる。**

クライアントから見て1つの操作である処理が、
複数の公開API呼び出しへ不自然に分割されていないか確認する。

例えば、

```text
prepare()
execute()
commit()
```

を常に一連の操作として呼ぶ必要があり、
クライアントから見ても1つの振る舞いである場合は、
より自然な公開APIへまとめるべきか検討する。

ただし、
テストコードを単純化するためだけに
公開APIを変更しない。

API設計は、
実際のクライアントにとって自然かどうかを基準にする。

# Domain Logicと外部依存

複雑なbusiness logicと、
mutableな共有依存を同じ責務へ持たせない。

可能な範囲で、

```text
Controller
    ↓
Domain Logic
    ↓
Result
    ↓
Controller
```

の構造を検討する。

## Domain Logic

Domain Logicは、

- business rule
- validation
- 判断
- 計算
- state transition

などの複雑なロジックを担当する。

可能な限り、

- immutableな値を扱う
- 外部状態を直接変更しない
- DB、filesystem、network、OS APIなどへ直接アクセスしない
- 入力から出力を求める

構造にする。

これにより、
出力値ベーステストで振る舞いを検証しやすくする。

## Controller

Controllerは、

- 外部依存から必要なデータを取得する
- Domain Logicへ入力を渡す
- Domain Logicの結果を外部へ反映する

ことを担当する。

Controllerはmutableな共有依存を扱ってよいが、
複雑なbusiness logicを持たせない。

**mutableかつ複雑なロジックを持つ責務を作らない。**

# 外部依存

- domain logicは、可能な範囲でDB・filesystem・network・OS API・framework API・現在時刻・乱数などの外部依存から分離する。
- 外部状態を必要とする場合は、処理内部で暗黙的に取得せず、境界から渡すことを検討する。
- 実行途中で得た結果を使って外部データを取得する必要がある場合は、必要な外部依存や取得操作を注入することを検討する。
- 外部依存の分離そのものを目的に、過度なinterfaceやabstractionを追加しない。
- テストしやすさだけを理由にproduction codeを不自然に歪めない。

# コメント

- 基本的にはそのプロジェクトへの前提知識がない人でも読めるように補足情報としてコメントを残す。
- 関数、クラスなど処理のまとまりやデータ型には、理解時間を短縮できる場合にDocumentationコメントを書く。
- 極端に短い場合や、名前と型だけで十分明らかな場合は省略してよい。
- 関数本体については、理解時間の短縮につながる場合に処理単位のコメントを書く。
- コメントで処理手順を説明する前に、意味のある処理単位を関数やメソッドへ切り出せないか検討する。
- 長い処理に説明コメントを追加して補うより、責務ごとに処理を分割することを優先する。
- コードの逐語的な説明は書かない。
- 設計意図・理由・制約など「なぜそうしているか」がコードから明らかでない場合はコメントする。
- コメントは `natural-expression` スキルを用いて自然な日本語で記述する。
- 複雑なアルゴリズムや直感的でない実装では、前提条件・選択理由・境界条件を記述する。
- 一時的なworkaroundや意図的に不自然な実装には、その理由と可能であれば解消条件を書く。
- 公開APIや利用方法・契約がコードだけでは明確でないinterfaceには、必要に応じてDocumentation commentを使用する。
- 不要なコードをコメントアウトして残さない。履歴はGitに任せる。
- `TODO` / `FIXME` は未完了事項や解決すべき問題を具体的に書く。
- 実装変更によってコメントが不正確になった場合は、同時に更新または削除する。

# 変更範囲

- タスクと関係のないリファクタリング、rename、dependency更新、style変更を混ぜない。
- 改善余地を見つけても、現在の変更に必要でなければ原則として変更しない。
- リファクタリングが必要な場合は、その変更を成立させるために必要な理由を説明できること。
- 行数を最小化することより、変更後のコードが既存設計と一貫し、理解しやすいことを優先する。

# 抽象化

- 重複して見えるという理由だけで共通化しない。
- 共通の意味や責務が存在する場合に抽象化する。
- 既存の抽象化で十分な場合、新しい抽象化を追加しない。
- 現在存在しない将来要件のためにgeneric化やconfigurationを増やしすぎない。
- 新しい型やinterfaceを追加する場合は、既存の同等概念がないか確認する。

# エラーと抑制

- 問題を回避するためだけにwarning・lint・errorを抑制しない。
- `allow(...)`、`eslint-disable`、`ts-ignore` などを使用する場合は、その理由が説明できること。
- 抑制が必要な場合は、可能な限り局所的な範囲に限定する。
- エラーを無視したり、失敗を成功として扱ったりしない。

# テスト

- observable behaviorが変わる場合、原則として対応するテストを追加または更新する。
- テストを通すためだけに、テスト削除・skip・assertionの弱体化・根拠のないexpected value変更を行わない。
- 既存テストが失敗した場合は、production codeとtestのどちらが仕様と一致していないかを確認する。
- テストしやすくするためだけにproduction codeを不自然に歪めない。
- Actが1つの公開操作で表現できない場合は、公開APIの責務が自然かを検討する。
- observable behaviorを確認するためにprivate stateの公開が必要になる設計は避ける。
- 具体的なテスト設計、粒度、Mock / Stub、AAAなどは `docs/test-guidelines.md` に従う。

# 完了条件

実装完了時には少なくとも以下を確認する。

- タスクに必要な変更だけが含まれている。
- 既存の設計・命名・コードスタイルと大きく矛盾していない。
- 不要な型・utility・abstractionを追加していない。
- 関係のないリファクタリングが混ざっていない。
- 複雑なdomain logicとmutableな共有依存が不自然に混在していない。
- observable behaviorと公開APIの境界が大きくずれていない。
- behavior changeに必要なテストがある。
- コメントが実装と一致している。
- warningやerrorを不自然に抑制していない。
- 不要なdead codeやdebug codeが残っていない。
