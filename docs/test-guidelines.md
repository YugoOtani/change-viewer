# テストガイドライン

このドキュメントは、本プロジェクトにおけるテスト設計・テスト実装の共通方針を定める。

テストの目的は、現在の実装を固定することではなく、
要求された振る舞いが将来のリファクタリング後も維持されていることを確認することである。

テストでは、

- 退行への耐性
- リファクタリングへの耐性
- 迅速なフィードバック

のバランスを考える。

特に単体テストでは、
高速なフィードバックを維持しながら、
実装詳細に依存した偽陽性を可能な限り避ける。

---

# 基本方針

- テストは実装詳細ではなく、クライアントから観察可能な振る舞いを検証する。
- privateな内部状態や内部処理を、外部から観察できないという理由だけで直接検証しない。
- 処理途中の状態を網羅的に確認せず、意味のある最終結果を検証する。
- 現在の実装構造を正しい前提としてテストケースを作らない。
- リファクタリングによって振る舞いが変わっていないにもかかわらず失敗するテストを増やさない。
- テストを通すためだけにproduction codeの構造を不自然に歪めない。
- 網羅性そのものを目的として、価値の低いテストを大量に追加しない。

---

# 観察可能な振る舞い

テスト対象のシステムについて、

**クライアントから観察できる結果**

を検証する。

観察可能な振る舞いには、例えば以下が含まれる。

- 公開APIの戻り値
- クライアントから参照可能な状態変化
- システム外部に対する意味のある作用
- 公開されたエラーや結果

一方、以下は原則として実装詳細として扱う。

- private methodが呼ばれたか
- 内部オブジェクトがどの順番で更新されたか
- 中間状態がどの値になったか
- スタブへ何回アクセスしたか
- 内部コンポーネント間でどのメソッドが呼ばれたか

公開された振る舞いを検証できる場合は、
内部状態やinteractionではなく最終結果を優先する。

---

# テスト対象の境界

システムは、

**自分の直下にあるシステムについて、クライアントから観察可能な振る舞いだけを検証する。**

それより下位のコンポーネントの実装方法は、
上位システムから見れば実装詳細として扱う。

例えば、

```text
Application Service
    ↓
Domain Service
    ↓
Repository
```

という構造でApplication Serviceをテストする場合、

Domain Service内部の処理手順やRepositoryへの細かなアクセス方法まで
Application Serviceのテストで固定しない。

各レベルのテストは、
そのレベルのクライアントから見える振る舞いを検証する。

---

# Arrange / Act / Assert

単体テストは原則として、

1. Arrange
2. Act
3. Assert

の3フェーズで構成する。

各フェーズはこの順番で1回ずつ記述する。

基本形:

```ts
const subject = createSubject();
const input = createInput();

const result = subject.execute(input);

expect(result).toEqual(expected);
```

## フェーズの区切り

通常は各フェーズを空行で区切る。

```ts
const subject = createSubject();

const result = subject.execute();

expect(result).toEqual(expected);
```

ArrangeやAssert内部でも空行が必要になり、
フェーズ境界が空行だけでは分かりにくくなる場合に限り、
コメントで区切る。

```ts
// Arrange
...

...

// Act
...

// Assert
...

...
```

単純なテストへ形式的に

`// Arrange`
`// Act`
`// Assert`

を付けない。

## 1テスト1振る舞い

1つのテストでは、
1つの意味のある振る舞いを検証する。

複数の独立した振る舞いを
1つのテストへまとめない。

複数のassertionが存在しても、
それらが1つの振る舞いの結果を表している場合は許容する。

## Actは原則として1つの公開API

Actフェーズは原則として、
1つの公開APIへの操作で表現する。

例:

```ts
const result = service.execute(command);
```

1つの振る舞いを成立させるために、

```ts
service.prepare();
service.execute();
service.commit();
```

のような複数の公開操作が必要になる場合は、

**それらを1つの公開APIとして表現すべき振る舞いではないか**

を検討する。

ただし、テストの形式に合わせるためだけに
production APIを統合しない。

クライアントから見ても1つの操作として扱うことが自然かどうかを基準に判断する。

---

# テストケースの粒度

- 1つのテストでは1つの振る舞いを検証する。
- 同じsetupを共有できるという理由だけで、異なる振る舞いをまとめない。
- テストを細かく分割すること自体を目的にしない。
- テストごとに固有で、名前を与えることで意図が明確になる処理は関数へ切り出す。
- テスト間で共有するmutableなグローバル状態を原則として使用しない。
- グローバル状態がなければ現実的に記述できない場合のみ、その理由を明確にして使用する。

---

# テスト名

テスト名には、

**どのように実装されているかではなく、何が起きるか**

を書く。

つまりHowではなくWhatを記述する。

Good:

- `returns_reviews_due_today`
- `rejects_invalid_review_date`
- `preserves_completed_state_after_reload`

Avoid:

- `calls_repository_once`
- `uses_review_filter`
- `invokes_normalize_before_save`
- `test_execute_method`

テスト名を変更せずに内部実装を置き換えられることを、
良い命名の目安の1つとする。

---

# パラメータ化テスト

入力値だけが異なり、
検証する振る舞いが同一の場合は、
複数の独立したテストをコピーするのではなく
パラメータ化テストを検討する。

例:

```text
1 → valid
2 → valid
3 → valid
```

がすべて

「有効な値を受け付ける」

という同一の振る舞いを検証している場合は、
パラメータ化できる。

一方、

- 正常系
- 境界値
- エラー処理

のように意味の異なる振る舞いを、
値が違うだけに見えるという理由で1つにまとめない。

---

# テストレベル

テストレベルは、

- 退行への耐性
- リファクタリングへの耐性
- フィードバック速度

のトレードオフを考えて選択する。

## 単体テスト

高速なフィードバックを重視する。

以下に適する。

- domain logic
- 純粋な計算
- validation
- state transition
- business rule

実装詳細との結合を避け、
リファクタリングへの耐性を維持する。

## 結合テスト

複数のコンポーネント間の実際の接続を確認する。

例:

- RepositoryとDB
- serialization
- adapter
- persistence
- frameworkとの境界

単体テストでは確認できないcontractを検証する。

## E2Eテスト

システム全体に近い振る舞いを確認し、
退行への耐性を高める。

一方で、

- 実行速度
- 原因特定の難しさ
- 環境依存

というコストが高い。

単体テストで十分確認できるものまで
E2Eで重複して大量に検証しない。

---

# モックとスタブ

Test Doubleは役割を区別して扱う。

## Mock

Mockは、

**システムからシステム外部へ向かう作用**

を置き換えるために使う。

例:

```text
System
  → Mail Service
```

メール送信自体がクライアントから観察可能な振る舞いである場合、

```text
メール送信が要求された
```

というinteractionを検証してよい。

Mockとのinteractionは、
それ自体がobservable behaviorである場合にのみ検証する。

## Stub

Stubは、

**システムが処理を行うために内部へ取り込むデータ**

を置き換えるために使う。

例:

```text
Repository
  → data
  → System
```

Stubはテスト対象へ入力を与えるためのものであり、

```text
repository.find() が1回呼ばれた
```

のようなStubとのinteractionは検証しない。

Stubとのやり取りは実装詳細として扱う。

## 判断基準

Test Doubleを使うときは、

```text
これは結果を与えるための依存か？
    → Stub

これは外部へ起こした作用を観察するための依存か？
    → Mock
```

を考える。

MockやStubというライブラリ上の型名ではなく、
テスト内で果たしている役割によって判断する。

---

# 出力値ベーステスト

複雑なdomain logicは、
可能な限り出力値ベースでテストできる構造を優先する。

出力値ベーステストでは、

```text
入力
 ↓
Domain Logic
 ↓
出力
```

の関係を直接検証する。

例えば、

```ts
const result = calculateSchedule(input);

expect(result).toEqual(expected);
```

のように、
入力に対して返された値を検証する。

出力値ベーステストは、

- 内部状態
- collaboratorとのinteraction
- 実行手順

への依存を減らしやすく、
リファクタリングへの耐性を高く保ちやすい。

複雑なbusiness ruleを、
可能な範囲でこの形式で検証できるようにする。

---

# Controllerのテスト

外部依存を扱うControllerでは、
domain logicのような出力値ベーステストだけでは
振る舞いを確認できない場合がある。

Controllerの責務は、

- 外部からデータを取得する
- domain logicへ渡す
- domainの結果を外部へ反映する

程度に保つ。

Controllerが外部へ起こす観察可能な作用については、
必要に応じてMockで検証する。

一方、

外部依存から取得したデータの使い方や
内部コンポーネント間の細かなinteractionを
過剰に固定しない。

---

# テストしやすいアーキテクチャ

良いテストを記述するためには、
production code側にも適切な境界が必要である。

## Observable BehaviorとPublic API

原則として、

**観察可能な振る舞いと公開APIの範囲を一致させる。**

クライアントから見える振る舞いは、
公開APIを通じて実行・観測できるようにする。

逆に、
クライアントに意味のない内部状態を
テストのためだけに公開しない。

## 1つの振る舞いと1つのAPI

クライアントから見て1つの操作であるものは、
可能な限り1つの公開APIで実行できるようにする。

テストのActが不自然に複数の公開APIへ分散する場合は、
API設計に問題がないか検討する。

## Functional Architecture

複雑なdomain logicとmutableな共有依存を
同じ責務へ持たせない。

原則として、

```text
Controller
    ↓
Domain Logic
    ↓
Result
    ↓
Controller
```

という分離を検討する。

### Domain Logic

- 複雑なbusiness ruleを担当する
- immutableな値を中心に扱う
- 外部依存を直接操作しない
- 入力から出力を計算する
- 主に出力値ベーステストで検証する

### Controller

- DB、filesystem、networkなどの共有依存を扱う
- domain logicに必要な入力を集める
- domain logicの結果を外部へ反映する
- mutableな処理を持つ場合でもロジックは単純に保つ
- 外部へのobservable interactionは必要に応じてMockで検証する

**mutableかつ複雑なbusiness logicを持つコードを避ける。**

---

# 実行途中で外部データが必要になる場合

処理途中で得られた値を使って、
さらに共有依存からデータを取得する必要がある場合がある。

その場合でも、
domain logic内部から暗黙的に共有依存へアクセスすることを避ける。

必要に応じて、

- 外部依存
- 必要な取得操作
- collaborator

を境界から注入する。

ただし、
テスト可能性だけを目的として
不要なinterfaceやabstractionを増やさない。

---

# テスト観点

テスト設計時は、必要に応じて以下を検討する。

- 正常系
- 境界値
- 異常系
- 状態遷移
- domain invariant
- persistence
- 入出力contract
- regression
- timezone / 日付境界
- concurrency
- retry / recovery
- duplicate operation / idempotency
- permission / authorization
- external dependency failure

すべてを機械的に適用しない。

要求・リスク・変更内容に応じて、
意味のあるものだけを選択する。

---

# テストデータ

- テストに必要な最小限のデータを使用する。
- 意味のない巨大fixtureを避ける。
- 重要な値がテストコードから読み取れるようにする。
- magic numberや意味不明な固定値を乱用しない。
- 共通fixtureによって前提が隠れる場合は、各テスト内で明示する。
- helperやbuilderはテストの意図を明確にする場合に使用する。

---

# 時刻・乱数・非決定性

## 時刻

- 現在時刻へ直接依存するテストを避ける。
- 時刻は可能な限り外部から渡す。
- `now()` の結果によって成功・失敗が変わるテストを書かない。
- timezoneが重要な場合は明示する。

## 乱数

- テスト結果が乱数によって不安定にならないようにする。
- 必要な場合はseed固定や依存注入を検討する。

## 非同期処理

- 固定時間のsleepへ依存しない。
- 完了条件を待つ。
- 非同期処理完了前にassertしない。

---

# リグレッションテスト

bug fixでは可能な限り、

1. bugを再現するテストを追加する
2. 期待どおり失敗することを確認する
3. production codeを修正する
4. テストが成功することを確認する

の順で進める。

再現テストが現実的でない場合は、
その理由を明示する。

---

# テストコードの品質

テストコードにもproduction codeと同様に可読性を求める。

- `docs/coding-guidelines.md` に従う。
- 意図は命名・関数分割・データ構造で表現する。
- Arrange / Act / Assertの構造を明確にする。
- 不要な抽象化や過度なDRY化を避ける。
- テスト間の依存を作らない。
- 実行順に依存しない。
- 他のテストへmutable stateを残さない。

テストコードでは、
多少の重複によって各テストの意図が明確になる場合は許容する。

---

# 最重要原則

良い単体テストは、

**現在の実装方法を確認するものではなく、
クライアントに約束した振る舞いが維持されていることを確認するもの**

である。

内部実装を変更してもobservable behaviorが変わらない限り、
可能な限りテストも変更せずに済む状態を目指す。
