# レビュー

## 変更概要

変更全体が何を実現しているかを1〜3文で説明する。

## 処理の流れ

主要な実行経路を簡潔に示す。

例:

`HTTP Request → updateUser → normalizeInput → repository.save`

各ノードについて必要なら一文だけ補足する。

### 1. `<意味のある変更名>`

**何を変えたか**

変更された振る舞いや責務を簡潔に説明する。

**なぜ**

その変更が必要になった理由を説明する。

**主な場所**

`path/to/file.ts` の `functionName` など、人間がコードを探せる粒度で示す。厳密な行番号は必須ではない。

**Context**

必要な場合だけ、内側から外側へ示す。

`変更箇所 → immediate semantic parent → semantic context`

各階層について、その親を見ることで何が分かるのかを短く説明する。

**関連**

他の変更単位との依存・前後関係があれば記載する。

同じ形式で主要な変更を続ける。

## 重要な設計判断

実装理解に重要な判断がある場合だけ箇条書きで記載する。

## 未確認事項

必要な場合だけ記載する。
