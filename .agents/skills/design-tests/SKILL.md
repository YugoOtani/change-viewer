# 目的

実装方法ではなく、

**クライアントから観察可能な振る舞いを正しいと判断するために必要なテスト**

を設計する。

また、テスト設計を通じて、

- observable behaviorとpublic APIが一致しているか
- 1つの振る舞いを1つの公開操作で実行できるか
- 内部状態を直接検証しなければ確認できない設計になっていないか
- 複雑なdomain logicとmutableな共有依存が分離されているか

を確認する。

このSkillではテストコードを実装しない。

# 入力

対象タスクの以下を確認する。

- 機能仕様
- `.ai/features/<feature-name>/tasks/<task-name>/task.md`
- `.ai/features/<feature-name>/tasks/<task-name>/plan-implementation.md`
- 受け入れ条件
- `docs/test-guidelines.md`
- `docs/coding-guidelines.md`
- 必要に応じて関連する既存テスト

`plan-implementation.md` がある場合は、
実装前にレビューされた主要な責務・境界・想定シグニチャとして使用する。

現在の実装詳細をテストケースの正しさの根拠にしない。

# 手順

## 1. 観察可能な振る舞いを特定する

タスクと仕様から、

**クライアントが最終的に何を観察できれば正しいと判断できるか**

を整理する。

例えば、

- 戻り値
- 公開された状態
- 外部へ起こる意味のある作用
- エラー
- 永続化後に観察できる結果

などを対象とする。

以下は原則として直接のテスト対象にしない。

- private state
- private method
- 内部処理順序
- 中間結果
- Stubとのinteraction

## 2. テスト対象の境界を決める

各振る舞いについて、

- どのシステムをテストするか
- そのシステムのクライアントは誰か
- クライアントから観察できる結果は何か

を明確にする。

上位システムのテストから、
下位コンポーネントの内部実装まで固定しない。

## 3. Actとなる公開APIを確認する

各振る舞いについて、

**クライアントがどの公開APIを呼び出すことでその振る舞いを開始するか**

を確認する。

原則としてActは1つの公開操作で表現できることを期待する。

例えば、

```text
Act:
service.execute(command)
```

で表せることが望ましい。

一方、

```text
service.prepare()
service.execute()
service.commit()
```

のように、
1つの振る舞いを成立させるために複数の公開APIが必要な場合は、

- クライアントから見ても本当に複数の操作なのか
- 1つの公開APIとして表現すべき責務ではないか

を検討する。

API設計上の問題が疑われる場合は、
テストケースを無理に作るのではなく設計上の論点として残す。

## 4. Assertする最終結果を決める

各テストでは、
処理途中の状態ではなく意味のある最終結果を確認する。

例えば、

```text
入力
 ↓
複数の内部処理
 ↓
最終結果
```

であれば、
内部処理を個別にassertせず最終結果を検証する。

## 5. 必要なケースを選ぶ

要求・リスクに応じて必要なものだけ選ぶ。

- 正常系
- 境界値
- 異常系
- 状態遷移
- 不変条件
- 永続化
- 入出力contract
- 並行処理
- タイムゾーン・日付
- retry / recovery
- regression

すべてのカテゴリを機械的に埋めない。

## 6. 同一振る舞いの値違いをまとめる

異なる入力値に対して
同一の振る舞いを検証する場合は、
パラメータ化テストを使用できないか検討する。

異なる意味を持つ振る舞いまで
1つのパラメータテストへまとめない。

## 7. Test Doubleを決める

必要な外部依存について、
MockとStubの役割を区別する。

### Stub

テスト対象へ入力を与える依存。

例:

```text
Repository → data → System
```

Stubとのinteractionは検証対象にしない。

### Mock

テスト対象からシステム外部へ起こす、
観察可能な作用を確認する依存。

例:

```text
System → Mail Service
```

外部作用そのものが振る舞いの場合に限り、
interactionを検証する。

## 8. テストレベルを選ぶ

目的に対して最も低コストで十分なレベルを選ぶ。

### 単体テスト

高速なフィードバックが重要で、
振る舞いを局所的に確認できる場合。

### 結合テスト

複数コンポーネント間の実際のcontract確認が必要な場合。

### E2E

システム全体としての退行検出に価値がある場合。

単体テストで十分な振る舞いを、
E2Eへ重複して大量に追加しない。

## 9. Domain Logicのテスト方法を確認する

複雑なdomain logicについては、
可能な限り出力値ベーステストで検証できるか確認する。

```text
input
  ↓
domain logic
  ↓
output
```

という形で、
入力に対する出力を直接確認できることを優先する。

内部状態やcollaboratorとのinteractionを
検証しなければ成立しない場合は、
production codeの責務分割に問題がないか検討する。

## 10. Controllerのテスト方法を確認する

Controllerについては、

- 外部からデータを取得する
- domain logicへ渡す
- 結果を外部へ反映する

という単純な責務になっているか確認する。

外部へ起こす観察可能な作用については、
必要に応じてMockで検証する。

Controller自身に複雑なbusiness logicが存在する場合は、
設計上の論点として残す。

# Planへのフィードバック

テスト設計中に以下が判明した場合は、
`plan-implementation.md` の再検討が必要な可能性を明示する。

- 1つの振る舞いを開始するために複数の公開API操作が必要
- observable behaviorを検証するためにprivate stateを見る必要がある
- domain logicが外部依存へ直接アクセスしている
- mutableな共有依存と複雑なbusiness logicが同じ責務にある
- クライアントから見た振る舞いと公開APIの境界が一致していない

このSkill自身が、
実装開始後のPlanをActualに合わせて変更しない。

実装開始前であれば、
人間の判断を経てPlanを修正してよい。

# 出力

出力先は必ず以下とする。

`.ai/features/<feature-name>/tasks/<task-name>/test-plan.md`

以下を簡潔に記載する。

```md
# テストPlan

## テストケース

- <検証する振る舞い>
  - 条件: <重要な前提>
  - Act: `<公開API>`
  - 期待結果: <observable result>
  - レベル: 単体 / 結合 / E2E / 手動
  - Test Double: <必要な場合のみ>

## 設計上の論点

問題がある場合のみ記載する。

- <テスト設計から見つかったAPI・責務上の問題>
```

テストコードの詳細な実装方法までは書かない。

# ルール

- `docs/test-guidelines.md` に従う。
- 現在の実装を正しい前提としてテストを設計しない。
- 実装詳細ではなくobservable behaviorを検証する。
- private stateを直接検証する前に、公開された最終結果で確認できないか考える。
- Stubとのinteractionを検証しない。
- Mockは外部へのobservable interactionに限定する。
- 同一振る舞いの値違いはパラメータ化を検討する。
- 出力値ベースで検証できるdomain logicを、interactionベースで固定しない。
- 受け入れ条件の単純な言い換えだけで終わらせない。
- 網羅性のためだけに不要なケースを増やさない。
