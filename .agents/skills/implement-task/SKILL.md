# 目的

指定された1つの実装タスクを、
既存アーキテクチャとプロジェクトルールを守りながら実装する。

事前に作成されたPlanがある場合は、
人間が理解した実装の骨格として参照する。

Planへの一致そのものを目的とはせず、
より自然な実装が必要な場合はPlanから変更してよい。

その場合は、実装後に差異と理由を明示する。

# 入力

対象タスクの以下を確認する。

- `.ai/features/<feature-name>/tasks/<task-name>/task.md`
- `.ai/features/<feature-name>/tasks/<task-name>/plan-implementation.md`
- `.ai/features/<feature-name>/tasks/<task-name>/test-plan.md`
- `AGENTS.md`
- 関連する仕様
- 関連する既存コードとテスト

`plan-implementation.md` と `test-plan.md` は存在する場合に確認する。

通常のPlan-firstフローでは `plan-implementation.md` を実装前に必ず確認する。

Planが存在せず、ユーザーからPlanを省略する指示もない場合は、
Planが存在しないことを報告し、実装を開始しない。

# 手順

## 1. タスクを完全に読む

以下を確認する。

- 目標
- 背景
- 依存関係
- 対象範囲
- 受け入れ条件
- 必要な検証
- リスク
- 対象外

依存タスクが未完了の場合は、その事実を明示する。

## 2. プロジェクトルールを確認する

関連する `AGENTS.md` を読む。

必要に応じて以下も確認する。

- architecture document
- ADR
- 関連仕様
- 関連タスク
- `docs/coding-guidelines.md`
- `docs/test-guidelines.md`

## 3. 既存実装を確認する

編集を始める前に、関連する既存コードを確認する。

以下を特定する。

- 影響範囲
- 既存の抽象化
- 既存パターン
- テスト構成
- architecture boundary
- 潜在的なリスク

既存の仕組みを利用できる場合は、
新しい仕組みを追加する前に再利用を検討する。

## 4. Planを確認する

`plan-implementation.md` がある場合は、
実装前に各項目を確認する。

特に以下を把握する。

- 各変更の目的
- 予定している責務分割
- 主要な境界
- 主要なデータの受け渡し
- 主要な想定シグニチャ

Planがある場合、
同じ問題についてゼロから別の実装方針を作り直さない。

Planを実装の出発点として使用する。

ただしPlanは実装を拘束する仕様ではない。

実際のコードを確認した結果、

- Planどおりでは不自然な実装になる
- 既存設計との整合性が悪くなる
- 不要な変換や状態が必要になる
- より単純で自然な方法が見つかる
- Plan作成時には分からなかった制約が判明する

場合は、より自然な実装を優先する。

Planから変更するためだけに事前承認を取り直す必要はないが、
変更内容と理由を実装結果へ残す。

実装結果に合わせて `plan-implementation.md` を書き換えない。

## 5. 実装する

以下を守る。

- `docs/coding-guidelines.md` を遵守する
- テスト実装時は `docs/test-guidelines.md` を遵守する
- 受け入れ条件を満たす
- scope外の変更を行わない
- 関係のないrefactoringを行わない
- 既存architecture boundaryを守る
- 既存の抽象化を尊重する
- 振る舞いを変更する場合は適切なテストを追加または更新する
- `test-plan.md` がある場合は、その検証観点を反映する

Planに記載されていないprivate helperや内部構造は、
既存コードに合う自然な形で決めてよい。

Plan上の想定シグニチャを維持するために
不自然なコードを書かない。

## 6. 検証する

タスクと `test-plan.md` に基づいて必要な検証を実行する。

実際に実行していない検証を成功したと報告しない。

失敗した検証や未実施の検証は明示する。

## 7. 実装結果を整理する

実装結果は必ず以下へ出力する。

`.ai/features/<feature-name>/tasks/<task-name>/implementation.md`

Planが存在する場合は、Planに書かれている内容を再説明するのではなく、
**Planとの差異を中心に記録する。**

基本形式:

```md
# 実装結果

## Planとの差分

差分がない場合:

- 主要な差分なし

差分がある場合:

- <対象>
  - Plan: <事前の想定>
  - Actual: <実際の実装>
  - 理由: <変更した理由>

## Planになかった変更

- なし

または、

- <追加で必要になった意味のある変更>
  - 理由: <なぜ必要になったか>

## 検証

- <実際に行った検証>: <結果>

## 未解決事項

- なし

または、

- <未解決事項>
```

Planのprivateな実装詳細との差は記録しない。

以下のような、実装の骨格に影響する差異を優先する。

- 責務分割の変更
- interface / public APIの変更
- 主要シグニチャの変更
- データの受け渡し方法の変更
- Planになかった主要なコンポーネントの追加
- architecture boundaryの変更

Planが存在しない場合は、
`implementation.md` に簡潔な実装概要を記録する。

# 完了チェック

- [ ] 対象外の変更がない
- [ ] Planを確認した
- [ ] Planを不自然に守るための実装をしていない
- [ ] Planとの差異を `implementation.md` に記録した
- [ ] 既存の抽象化・設計を尊重している
- [ ] 適切な粒度で責務を分割している
- [ ] 振る舞いの変更に対応するテストを追加または更新した
- [ ] 必要な検証結果を記録した
