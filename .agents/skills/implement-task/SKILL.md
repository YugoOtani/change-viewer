# 目的

指定された1つの実装タスクを、
既存アーキテクチャとプロジェクトルールを守りながら実装する。
変更範囲をできるだけ限定し、レビュー可能な状態に保つ。

# 手順

## 1. タスクを完全に読む

以下を確認する。

- 目標
- 背景
- 依存関係
- 対象範囲
- 受け入れ条件
- 必要な検証
- リスク
- 対象外

依存タスクが未完了の場合は、
その事実を明示する。

## 2. プロジェクトルールを確認する

関連する `AGENTS.md` を読む。

必要に応じて以下も確認する。

- architecture document
- ADR
- 関連仕様
- 関連タスク

## 3. 既存実装を調査する

編集を始める前に、
関連する既存コードを確認する。

以下を特定する。

- 影響範囲
- existing abstraction
- existing pattern
- test structure
- architecture boundary
- potential risk

既存の仕組みを利用できる場合は、
新しい仕組みを追加する前に再利用を検討する。

## 4. 実装方針を決める

以下を意識する。

- 最小限で一貫した変更
- 既存アーキテクチャとの整合
- scope外の変更を避ける
- 不要なrefactoringを避ける

## 5. 実装する

- 実装時は`docs/coding-guidelines.md`のコーディングガイドラインを遵守する。
- テスト実装時は `docs/test-guidelines.md` を遵守する。
- 受け入れ条件を満たす実装を行う。
- 振る舞いを変更する場合は、実装担当が同じタスク内で適切なテストを追加または更新する。
- `test-plan.md` がある場合は、その検証観点をテストへ反映する。
- Tauri commandへdomain logicを書かない。
- UIからpersistenceへ直接アクセスしない。
- 既存architecture boundaryを守る。
- 完了チェックリスト
  * [ ] 受け入れ条件を満たした
  * [ ] 対象外の変更がないことを確認した
  * [ ] レビュアー向けに適切にコメントを残した
  * [ ] 適切な粒度で関数・クラスへの切り出し、抽象化を行っている
  * [ ] 既存の抽象化・設計を尊重している
  * [ ] 振る舞いの変更に対応するテストを追加または更新した

## 6. 実装結果を整理する

最後に以下を `.ai/features/<feature>/tasks/<task>/implementation.md` にまとめる。

- 変更した内容
- 変更理由
- 主な変更箇所
- 追加・変更したテスト
- 受け入れ条件への対応
- 未解決リスク
- 未検証事項
