# 目的

実装を開始する前に対象コードを確認し、

- 何のために変更するか
- どの責務を変更・追加するか
- コンポーネント間の境界をどう変えるか
- 主要な境界のシグニチャをどうする想定か

を、実装者が短時間で理解できる粒度に整理する。

詳細設計書を作ることは目的としない。

**人間が実装の骨格を理解した状態でAIに実装を任せ、
実装後はPlanとの差を重点的に確認できる状態を作る。**

# 入力

対象タスクの以下を確認する。

- `.ai/features/<feature-name>/tasks/<task-name>/task.md`
- `AGENTS.md`
- 関連する機能仕様
- 関連する既存コード
- 関連する既存テスト
- 既存の抽象化・architecture boundary

タスク記述だけから実装方針を推測しない。

# 基本方針

Planでは、

**「何のために」＋「実装上何を変えるか」**

を基本単位とする。

例:

- VSCode APIへの依存をアプリケーション側から切り離すため、`ConfigFileEventSource` インターフェースを導入する
- 変更対象を呼び出し側へ伝えるため、`onDidChange` のlistenerへ `uri` を渡す
- 設定変更を表示へ反映するため、変更通知を受けてレビュー状態を再読込する

ファイル単位や実装順序ではなく、意味のある変更単位で整理する。

# 手順

## 1. 対象コードを確認する

今回の変更に関係するコードを確認する。

最低限、以下を把握する。

- 現在どの責務がどこにあるか
- 関係する主要な型・関数・インターフェース
- データやイベントがどこからどこへ渡るか
- 既存の依存関係
- 今回変更する境界

必要以上にコードベース全体を調査しない。

## 2. 変更の目的を特定する

単に「何を追加するか」ではなく、

**なぜその変更が必要なのか**

を確認する。

例えば、

「インターフェースを追加する」

ではなく、

「VSCode APIへの依存をアプリケーション側から切り離すため、インターフェースを追加する」

と捉える。

理由を必要以上に深掘りせず、実装判断を理解するのに必要な範囲だけ記述する。

## 3. 意味のある変更単位に分ける

変更を、実装者が理解しやすい責務単位に分ける。

良い例:

- 新しい情報を渡せるようにする
- 外部APIへの依存を境界の外へ出す
- 状態変更を通知できるようにする
- 既存処理から責務を切り出す
- 新しい状態を表示へ反映する

避ける例:

- `foo.rs` を変更する
- `bar.ts` を変更する
- 30行目を修正する

ファイルは変更箇所を特定する補助情報として扱い、Planの主語にはしない。

## 4. 主要な想定シグニチャを示す

新規または変更される主要な境界については、
実装前時点の想定シグニチャをPlanに含める。

対象は主に以下とする。

- public API
- interface
- 外部との境界になる関数・メソッド
- コンポーネント間でデータを受け渡す関数
- 責務や依存関係を理解するうえで重要な型

例:

```ts
onDidChange(
    listener: (uri: string) => void
): ConfigEventSubscription;
```

private helperや局所的な関数については、原則として事前にシグニチャを決めない。

## 5. シグニチャで実装を拘束しない

Plan上のシグニチャは、

**実装前に設計の骨格を理解し、
実装後に差分を確認するための予測**

として扱う。

実装時に想定シグニチャを維持することで、

- 不自然なデータ変換が必要になる
- 不要な状態を保持する必要がある
- 責務の境界が不自然になる
- 既存アーキテクチャとの整合性が悪くなる
- より自然なAPI設計を妨げる

場合は、Planより自然な実装を優先する。

その場合は、実装後にPlanとの差分として確認する。

## 6. 実装詳細を決めすぎない

以下は原則としてPlanには含めない。

- private helperの構成
- 一時変数
- 細かな条件分岐
- 内部アルゴリズム
- 実装行数
- 詳細な疑似コード
- ライブラリAPIの細かな呼び出し手順

これらは実装担当に任せる。

ただし、責務やarchitecture boundaryに影響する場合はPlanに含める。

# 記述ルール

`.ai/templates/plan-implementation.md` のフォーマットに従う。

出力先は必ず以下とする。

`.ai/features/<feature-name>/tasks/<task-name>/plan-implementation.md`

各Plan項目は原則として、

**「<目的・理由>のため、<実装上の変更>を行う」**

という構造にする。

必要に応じて、その直下に想定シグニチャを書く。

設計用語は必要に応じて使用してよい。

例えば、

- 抽象化する
- 分離する
- 委譲する
- インターフェースを導入する

などを一律に避けない。

ただし、設計用語だけでは意図が分かりにくい場合は、
その設計判断によって何を変えたいのか具体化する。

避ける:

> ファイル監視を抽象化するため、インターフェースを導入する。

推奨:

> VSCode APIへの依存をアプリケーション側から切り離すため、`ConfigFileEventSource` インターフェースを導入する。

# Planの粒度

Planは短時間でレビューできることを優先する。

主要な変更を数個の箇条書きに収める。

細かな変更を独立したPlan項目として増やしすぎない。

複数の変更が同じ目的に属する場合はまとめる。

人間がPlanを読んだあと、

**「だいたいこういう構造に変わる」**

と説明できれば十分とする。

# Planの扱い

Planは実装を拘束する仕様ではない。

一方で、実装前に人間が理解した内容との比較基準として使用するため、
実装開始後に実装結果へ合わせてPlanを書き換えない。

実装前のレビューによって方針自体を変更する場合は、
実装開始前にPlanを更新してよい。

実装開始後にPlanと異なる実装が必要になった場合は、
Planを維持したまま、実装結果との差として扱う。

# 避けること

- コードを確認せずPlanを作る
- タスク記述をそのまま言い換える
- ファイル変更一覧をPlanにする
- 実装順序だけを書く
- 詳細な疑似コードを書く
- private helperまで事前設計する
- すべてのシグニチャを列挙する
- Planのシグニチャに実装を無理に合わせる
- 抽象化自体を目的にする
- 将来必要かもしれない設計を追加する
- Planを長くすることで品質を上げようとする
- 実装開始後にActualへ合わせてPlanを書き換える

# 最重要原則

Planで決めるのは、

**実装の骨格**

までとする。

人間は、

- 目的
- 責務
- 境界
- 主要なデータの受け渡し
- 主要な想定シグニチャ

を理解する。

内部実装は実装担当に任せる。

Planは、

**実装前に理解するための地図であり、
実装を縛る設計書ではない。**
