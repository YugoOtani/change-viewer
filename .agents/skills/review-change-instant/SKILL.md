# 目的

実際のコード変更を読み、人間がコードをすべて追わなくても、

- 何を実現する変更か
- どこから処理が入り、どこで変更が効くか
- 各変更が何をしており、なぜ必要か
- その変更がアプリケーション全体の何の一部か

を短時間で把握できる Markdown を作る。

これは詳細なコードレビューや承認判断を目的としない。変更内容の理解に必要な情報を優先し、差分の逐語的な説明や網羅的な指摘は行わない。

# 基本方針

## 実際のコードを基準にする

指定された base / target commit の差分と変更後コードを確認する。
指定されなかった場合は未コミットの変更を対象に行う
タスクや仕様に書かれた意図と実装が異なる場合は、実際の実装を説明する。確認できないことを推測で補わない。

`.ai/features/<feature>/tasks/<task>/implementation.md`は実装エージェントが作成した実装メモであり不明点がある場合には参照してよい。ただし、実装メモの内容をそのままレビュー判断の根拠にせず、実際のコードと照合して確認する。

## 「差分」ではなく「実装」を説明する

ファイル順や diff hunk 順に説明するのではなく、人間にとって意味のある責務・処理単位でまとめる。

説明では特に次を重視する。

1. 変更前後で何が変わったか
2. なぜその変更が必要なのか
3. 処理全体のどこで使われるのか
4. 他の変更とどうつながっているのか

コードを言い換えるだけの説明は避ける。

# 手順

## 1. 変更全体を把握する

差分、変更後コード、必要に応じて仕様やタスクを確認し、この変更全体が実現しようとしていることを1〜3文で整理する。
細かな実装内容ではなく、ユーザー機能・システム動作・設計上の目的を説明する。

## 2. 処理の流れを特定する

変更が実行時にどのように使われるかを確認する。可能なら、

`入口 → 主要な処理 → 今回の変更 → その後の処理`

という形で、人間が読むべき主要な流れを整理する。すべての関数呼び出しを列挙せず、変更の意味を理解するために必要なノードだけを残す。複数の独立した処理がある場合は、流れを分ける。

## 3. 意味のある変更単位に分ける

変更を、ファイルや hunk ではなく意味のある責務でまとめる。各変更単位について次を説明する。

- **何を変えたか**
- **なぜ変えたか**
- **主なコード位置**
- **他の変更との関係**

複数ファイルにまたがっていても、一つの責務なら一つの変更単位として説明してよい。細かな rename、format、機械的変更は、理解に必要でなければ独立した項目にしない。

## 4. 外側の semantic context を説明する

変更箇所だけでは役割が分かりにくい場合に限り、その変更が「何の一部なのか」を説明する。単なる AST 上の親や直近の呼び出し元ではなく、**意味的な親（semantic parent）**を選ぶ。原則として、

`変更箇所 → immediate semantic parent → より大きな semantic context`

の順で考える。

### immediate semantic parent

その変更が「何の処理を実現する一部なのか」を最も直接説明できるコード単位。直近の関数が単なる wrapper、delegate、utility で意味を増やさない場合は飛ばしてよい。直近の関数がimmediate semantic parent で十分に役割が明確なら、より大きな context は追加しない。

### 最外側の context

その context を見れば、

**「この変更はアプリケーション全体の何の機能・処理に属するのか」**

を説明できる**最小の単位**まで遡る。

それ以上の親が新しい意味を与えない場合は追加しない。Router、framework、application entrypoint まで機械的に遡らない。

通常は 1〜3 階層程度で十分とする。

例:

`入力値の正規化 → ユーザー更新処理 → ユーザー更新 API`

ただし「ユーザー更新処理」だけでシステム上の役割が十分明確なら、API まで遡らなくてよい。

## 5. 重要な設計判断を抽出する

実装を理解するうえで重要なものだけを短く記録する。

例:

- 新しい責務分割
- 状態の保持場所の変更
- interface / API の変更
- エラー処理方針
- 既存設計を再利用した理由
- 一見不自然だが意図のある実装

単なるコード上の事実を重複して書かない。

## 6. 未確認事項を整理する

実装理解に影響する未確認事項がある場合だけ記載する。

例:

- 呼び出し元が一部確認できていない
- 仕様上の意図と実装の対応が不明
- 外部 API の挙動を確認できていない

問題がなければ、この節は省略してよい。

# 出力

`.ai/templates/review.md`のフォーマットに従って出力する
出力先は各タスクの`.ai/features/<feature>/tasks/<task>/review.md`とする。
すでに存在する場合はファイル名の末尾に連番を付けて保存する。

# 説明の粒度

この Markdown を読んだ人が、その後コードを見る際に、

- 最初にどこを読めばよいか
- そのコードが何のために存在するか
- なぜ今回変更されたか
- 一段外側を見るならどこを見るべきか

が分かる状態を目標とする。

すべての変更行を説明することは目標にしない。

説明量が増える場合は、コードの詳細を追加するより、処理の流れと semantic context を優先する。
