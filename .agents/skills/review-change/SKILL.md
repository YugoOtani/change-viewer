# 目的

実際のコード変更を、人間が短時間で理解・判断できる形に整理する。

1. 変更を意味のある Change Unit（CU）に分け、実装内容と変更理由を説明する。
2. 処理の流れに沿った Review Route と、必要最小限の外側のコード参照を作る。
3. 仕様・テスト・実コードを照合し、検証結果、リスク、人間が判断すべき論点を記録する。

最終的な承認・却下は行わない。Change Viewer の入力 JSON とレビュー判断を混同しない。

# 参照

レビュー開始前に、対象に応じて以下を確認する。

- `AGENTS.md` と `.ai/policies/` の関連規則
- `src/input.schema.json`（入力の構造・型の正本）
- `docs/spec.md`（入力の意味・検証規則の正本）
- `docs/architecture.md`、`docs/coding-guidelines.md`、`docs/test-guidelines.md`
- 機能仕様、タスク、テスト計画、実装理由
- 指定された基準・対象コミット間の実際の差分と、両コミットのソースコード

Git 操作やファイル変更は、`AGENTS.md` とユーザーの指示が許す範囲で行う。差分やコミットを確認できない場合は推測で補わず、不足している根拠を報告する。

# 基本方針

## 実装の説明とレビュー判断を分離する

`review.json` は Change Viewer に渡す変更説明と閲覧案内に限定する。CU の `summary` は実装の短い要約、`reason` はその変更を行った理由であり、良し悪しの評価を書く欄ではない。Route の `text` は、その順で読む理由や処理上のつながりを説明する。

仕様との整合性、リスク、検証結果、人間レビューの論点は、補助成果物 `review-notes.md` に記録する。JSON にスキーマ外のフィールドを追加したり、`reason` や Route の `text` に評価を押し込んだりしない。

`.ai/features/<feature>/tasks/<task>/implementation.md`は実装エージェントが作成した実装メモであり不明点がある場合には参照してよい。ただし、実装メモの内容をそのままレビュー判断の根拠にせず、実際のコードと照合して確認する。

## 実際のコードを基準にする

実装理由だけを根拠に変更内容を説明しない。指定された二つのコミットの実際の差分とコードを確認し、意図と実装が異なれば実装を優先する。未実行の検証を成功と書かない。コード本文や仕様本文を JSON にコピーしない。

# 手順

## 1. レビュー対象と変更全体を確定する

対象リポジトリの基準コミットと対象コミットを確認する。両方ともそのリポジトリで commit に解決できる完全長の小文字の object ID とする。差分は `baseCommit` から `targetCommit` への直接比較とし、merge-base や Working Tree の変更を混ぜない。

タスク、仕様、差分、変更後コードを照合し、達成しようとしていること、実際に変わった振る舞い、影響した領域、仕様外の変更、新しい設計判断を整理する。参照できない資料や未確認の事実は明示する。

## 2. CU に分ける

ファイルの羅列や機械的な hunk 分割ではなく、人間にとって意味のある責務で変更をまとめる。ただし、**一つの CU が指せる変更は一ファイル内だけ**とする。複数ファイルにまたがる一つの機能は、ファイルごとの CU と Review Route で関係を表す。同じファイル内の離れた変更は、一つの責務なら一つの CU の複数 `edits` にできる。CU 同士に親子関係は設けない。

各 CU には一意な `id`、一行程度の `summary`、変更の目的・理由を示す `reason` を付ける。`summary` は何を変えたか、`reason` はなぜ必要かを簡潔に書く。原則として主要な変更を CU で説明するが、変更行の網羅は必須ではない。割り当てない実差分がある場合は、補助レポートでその理由を説明する。

## 3. ファイルと変更行を指定する

CU の `file` に、基準側の `basePath` と対象側の `targetPath` を両方記録する。存在しない側は `null` とし、両方 `null` にはしない。名前変更は両方のパスを記録する。パスはリポジトリルートからの相対パスとし、絶対パスや `..` によるルート外参照を使わない。

`edits` は一件以上とし、各要素に `base` と `target` を必ず記録する。存在しない側は `null` とし、両方 `null` にはしない。存在する側の `startLine` と `lineCount` は、該当コミットの**実際の変更行**に対応する一始まりの正整数とする。連続する変更行ごとに範囲を作り、離れた箇所を一つの広い範囲に含めない。追加のみ・削除のみの編集では該当しない側を `null` とする。

差分の行位置は実際の Git 内容と照合する。ソースの行数から推測した範囲、変更されていない行を含む範囲、存在しないパスを記録しない。バイナリや権限変更など行で表せない変更には行単位の CU を作れないため、未割当差分として扱う。

## 4. 外側の文脈を指定する

CU 単体では「この変更が何の処理の一部なのか」が分かりにくい場合、`contextChain` に外側のコードを指定する。単なる字句上・AST 上の親ではなく、**人間が変更の役割を理解するための意味的な親（semantic parent）**を選ぶ。

`contextChain` は、CU のすぐ外側にある意味的な親から、より大きな処理へ向かって並べる。原則として次の順で考える。

`CU → immediate semantic parent → 上位の semantic context`

**immediate semantic parent** は、その CU が「何の処理を実現する一部なのか」を最も直接説明するコード単位とする。直近の関数やクラスが単なる委譲・ラッパーで意味を増やさない場合は飛ばしてよい。

上位の context は、内側の context に対して新しい役割・制御・状態・副作用・インターフェース上の意味を与える場合だけ追加する。単に呼び出しているだけの階層は追加しない。

Chain は、**その context を見れば変更がアプリケーション全体のどの機能・処理に属するか説明できる、最小の意味ある単位**に到達したところで止める。ルータ、フレームワーク内部、アプリケーション起動処理などまで機械的に遡らない。

例えば、

`値変換 helper → 注文確定処理 → 注文 API`

で注文 API を見れば変更のシステム上の役割が分かるなら、そこを最外側とする。一方、注文確定処理だけで十分に役割が明確なら API まで追加しない。

各 `ContextReference` には次を記録する。

- `relation`: `controlFlow`、`stateFlow`、`sideEffect`、`interface`
- `description`: **この親が CU の理解に何を追加するか**
- `location`: `revision`、`path`、`startLine`、`endLine`

不要な場合は空配列とする。context の数を増やすこと自体を目的にせず、通常は 1〜3 階層程度に収める。

## 5. Review Route を作る

`reviewRoutes` を一件以上作り、各 Route に一意な `id`、短い `title`、一件以上の `steps` を付ける。ステップの配列順を推奨閲覧順とする。処理の入口、変更が効く箇所、その後の流れが分かる順に並べる。

- `kind: "cu"`: `cuId` と `text` を持つ。`cuId` は存在する CU の ID とし、`text` にはその順に CU を読む理由や前後とのつながりを書く。
- `kind: "code"`: `location` と `text` を持つ。親コード以外に読むべき既存コードを、実在するソース位置で示す。
- `kind: "explanation"`: `text` のみを持つ。コード位置を伴わない処理上のつながりを説明する。

同じ CU を複数の Route で参照してよい。Route に含まれない CU も入力として有効だが、意図せず抜けていないか確認する。Route の説明だけでソース参照や差分を代用しない。

## 6. 検証結果とリスクを記録する

各 CU について仕様・設計・domain rule・テスト・実コードを照合する。不要な変更、エラー処理、コメントの妥当性も確認する。テスト成功だけで仕様や設計の妥当性を保証しない。

`.ai/policies/risk.md` などの risk policy に従い、各 CU のリスクを `low`、`medium`、`high` で判断する。振る舞い、永続データ、アーキテクチャ境界、権限・セキュリティ、破壊的操作、エラー処理、並行性、波及範囲、仕様上の不確実性を考慮する。コード量だけでリスクを高くしない。

人間による判断が必要なら、対象 CU と具体的な確認事項を示す。「問題がないか確認する」のような抽象的な依頼は避ける。問題がない場合、論点を無理に作らない。

実際に行われた検証は、実行内容、結果、確認できた範囲を記録する。実行結果を確認できない検証は未実施または未確認として扱い、成功としない。これらの判断と、関連する仕様・テストへの参照は `review-notes.md` にまとめる。独立した `evidence.json` は作らない。

## 7. 出力を検証する

`review.json` の全フィールドと型を `src/input.schema.json` で検証し、スキーマ外の項目を残さない。加えて `docs/spec.md` の意味上の制約を確認する。特に、コミット ID の解決、ID の一意性、CU ステップの参照先、パス、`SourceLocation` の範囲、`edits` と実差分の一致を確認する。構造検証だけで意味上の整合性まで確認済みと報告しない。

# 出力

主要成果物は `.ai/features/<feature>/tasks/<task>/review.json` とする。JSON は `src/input.schema.json` に完全に従い、最上位に次の五項目だけを置く。

- `schemaVersion`: `1`
- `baseCommit`: 完全長の基準コミット ID
- `targetCommit`: 完全長の対象コミット ID
- `reviewRoutes`: 一件以上の Review Route
- `changeUnits`: CU の配列

各 Route、ステップ、CU、ファイル、編集、文脈参照、ソース位置もスキーマで許されたフィールドだけを使う。旧形式の `implementation`、`review`、`references`、`evidence`、`risk`、`human_review_required`、`summary.title` などは JSON に入れない。ソース本文や資料本文も入れない。

補助成果物 `.ai/features/<feature>/tasks/<task>/review-notes.md` には、全体のレビュー結果と推奨アクション、CU ごとの評価・リスク・人間レビューの論点、検証結果、参照した仕様・テスト、未割当差分や未確認事項を日本語で記録する。JSON と別の判断資料であることを明示する。自由形式の Markdown を Change Viewer の入力として扱わない。

スキーマに必要な値を根拠を持って埋められない場合は、架空のコミット ID・行範囲・参照先で形式だけ整えない。不足を報告し、入力に使える `review.json` が完成したとは述べない。

# 完了条件

- 主要な変更が、ファイル境界を守った CU として説明されている。
- 各 CU の `summary`、`reason`、`edits` が実際の変更と一致している。
- Review Route が閲覧順と処理のつながりを示している。
- 必要な文脈参照が実在するコード位置を指している。
- 検証結果、CU ごとのリスク・評価、人間レビューの論点、全体の推奨アクションが補助レポートにある。
- `review.json` が `src/input.schema.json` と `docs/spec.md` の制約に適合している。
