# 目的

コードリーディング時の理解コストを下げるために、
コードを意味のある処理ブロックへ分け、それぞれの役割を要約するコメントを付与する。

コメントは、コードの各行を日本語へ翻訳するためのものではない。

コメントだけを上から順に読んだときに、
その関数・メソッド・処理の主要な流れを概ね把握できる状態を目指す。

設計判断の理由を説明する `Why` コメントよりも、
処理ブロックが何を達成しているかを示す `What` コメントを優先する。

# 基本方針

コメント内容は、以下の優先順位で決定する。

1. その処理ブロックが何を達成しているか
2. 前後の処理の中でどのような役割を持つか
3. コードだけでは分かりにくい重要な理由・制約
4. 実装方法そのもの

原則として 1 と 2 をコメントする。

3 は理解に重要な場合のみ補足する。

4 のような、コードをそのまま自然言語へ置き換えただけのコメントは避ける。

# 手順

## 1. 処理全体の目的を把握する

コメントを追加する前に、対象となる関数・メソッド・処理全体を読む。

以下を把握する。

- 入力は何か
- 最終的に何を生成・更新・返却するか
- 主な副作用は何か
- 外部サービスやRepositoryとのやり取りはあるか
- 処理がどのような段階に分かれているか

個々の行を見る前に、処理全体の流れを把握する。

## 2. 意味のある処理ブロックへ分割する

コードを1行単位ではなく、
1つの目的を達成する意味的な処理ブロックへ分割する。

処理ブロックの例:

- 入力の取得
- 入力の解析
- 入力値の検証
- 対象データの抽出
- 検索条件の構築
- データ取得
- データの変換・正規化
- データの集約
- 状態更新
- 外部サービスへの問い合わせ
- 永続化
- レスポンス構築
- エラー処理
- 後続処理の準備

複数の文が1つの目的を達成している場合は、
それらを1つの処理ブロックとして扱う。

## 3. 各処理ブロックの役割を要約する

各ブロックについて、

「このコードはどう実装しているか」

ではなく、

「このブロックによって何が達成されるか」

を考える。

可能であれば、コード内の変数名やAPI名より一段抽象度を上げて表現する。

悪い例:

```ts
// usersをfilterする
const activeUsers = users.filter(...);

// activeUsersをmapする
const userIds = activeUsers.map(...);
```

良い例:

```ts
// 通知対象となるユーザーを抽出し、送信先一覧を組み立てる
const activeUsers = users.filter(...);
const userIds = activeUsers.map(...);
```

## 4. 処理フローを理解するために有効なコメントだけを残す

すべての処理ブロックへ機械的にコメントを付けない。

コメントを追加することで、
処理全体の流れを追いやすくなる箇所を優先する。

特に以下を優先する。

- 処理のフェーズが切り替わる箇所
- 複数行で1つの意味を持つ箇所
- データの意味が変わる箇所
- 外部システムとの境界
- 状態を変更する箇所
- 後続処理の前提を作る箇所
- コードを数行読む必要があるが、一言で役割を説明できる箇所

逆に、以下には原則としてコメントを付けない。

- 単純な代入
- 自明なgetter呼び出し
- 関数名だけで役割が十分分かる処理
- コメントがコードの直訳にしかならない処理

## 5. 必要な場合のみ理由・制約を補足する

重要な設計判断や制約がある場合は、
処理内容の説明に加えて理由を補足してよい。

ただし、理由だけを書いて処理内容が分からなくならないようにする。

避ける例:

```ts
// 無効なユーザーへ送信しないため
const activeUsers = users.filter(...);
```

推奨例:

```ts
// 通知対象を有効ユーザーに限定し、誤送信を防ぐ
const activeUsers = users.filter(...);
```

処理内容と理由の両方が重要な場合は、
「何をしているか」を先に表現する。

# コメントの粒度

コメントは、基本的に処理ブロックの先頭へ配置する。

以下のような細かすぎるコメントは避ける。

```ts
// ユーザー一覧を取得する
const users = await repository.findAll();

// 有効なユーザーを抽出する
const activeUsers = users.filter((user) => user.isActive);

// IDを取得する
const userIds = activeUsers.map((user) => user.id);

// 通知を送る
await send(userIds);
```

処理の意味に合わせてまとめる。

```ts
// 通知対象のユーザーを抽出し、送信先一覧を組み立てる
const users = await repository.findAll();
const activeUsers = users.filter((user) => user.isActive);
const userIds = activeUsers.map((user) => user.id);

// 対象ユーザーへ通知を送信する
await send(userIds);
```

# コメントの抽象度

コメントはコードより一段高い抽象度を目指す。

コード:

```ts
const normalized = responses
    .filter((response) => response.status === "success")
    .map(toDomainModel);
```

避ける:

```ts
// successのresponseだけfilterしてDomainModelへmapする
```

推奨:

```ts
// 正常に取得できたレスポンスを後続処理用のドメインデータへ変換する
```

ただし、抽象度を上げすぎて具体的な処理内容が失われないようにする。

避ける:

```ts
// データを処理する
```

# 関数・メソッド内のフローを意識する

コメント単体の品質だけでなく、
コメントを上から読んだときに処理の流れになることを重視する。

例:

```ts
// リクエスト内容を検証する
...

// 入力から検索条件を構築する
...

// 条件に一致するデータを取得する
...

// 取得結果を画面表示用の形式へ変換する
...

// 処理結果を返却する
...
```

コメントだけ読むことで、

検証
→ 検索条件構築
→ データ取得
→ 表示用変換
→ 返却

という主要な処理フローを把握できる状態が望ましい。

# 既存コメントの扱い

既存コメントがある場合は、そのまま残すことを前提にしない。

以下の場合は修正または削除する。

- コードをそのまま説明している
- 現在の実装と一致していない
- Whyだけが書かれていて処理内容が分からない
- 細かすぎるコメントが大量にあり、処理フローを追いにくい
- 複数コメントを1つの処理要約へまとめられる

一方で、以下は可能な限り保持する。

- コードから復元できない業務上の制約
- 外部仕様による制約
- 非自明なアルゴリズム上の理由
- バグ回避や互換性維持に関する重要な背景

必要に応じて、処理要約コメントと統合する。

# コメントの文体

簡潔な現在形で記述する。

推奨:

- 対象データを抽出する
- レスポンスを内部形式へ変換する
- 更新対象をまとめて永続化する
- 後続処理に必要な情報を組み立てる

冗長な表現は避ける。

避ける:

- ここでは〜を行っている
- 以下の処理では〜する
- このコードによって〜が実行される

コメント自体を見出しのように読める表現を優先する。

処理要約の動詞は `natural-expression` の「実際の動作を表す」に従い、そのブロックが何をするか分かる言葉を選ぶ。

# 禁止事項

以下のコメントは原則として追加しない。

## コードの直訳

```ts
// countを1増やす
count += 1;
```

## 構文の説明

```ts
// for文でitemsをループする
for (const item of items) {
```

## 関数名と同じ説明

```ts
// ユーザーを取得する
const user = await getUser();
```

## 情報量のない抽象表現

```ts
// 必要な処理をする
```

```ts
// データを加工する
```

## 不要な設計意図の推測

コードや仕様から確認できない設計理由を推測してコメントしない。

理由が明確でない場合は、
確認できる処理内容だけを書く。

# 完成条件

コメント追加後、以下を確認する。

- コメントだけを上から読んで主要な処理フローを概ね把握できる
- 各コメントが、その直後の複数行または意味的な処理単位を要約している
- コードを単純に日本語へ翻訳したコメントが増えていない
- Whatの説明よりWhyの説明が中心になっていない
- コメントの粒度が細かすぎない
- コメントがないと理解しづらい処理の境界が適切に示されている
- コードから確認できない意図を推測していない
- コメントを読むことで、コードを読むべき箇所を絞り込める

最後に、コメントだけを順番に読み直す。

コメント列だけで処理概要が成立していない場合は、
処理ブロックの分割またはコメントの抽象度を見直す。
