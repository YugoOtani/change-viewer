# 目的

実装済みの変更について、仕様の正しさを詳細にレビューする前に、

- プロジェクトルールに従っているか
- 既存アーキテクチャや抽象化を壊していないか
- 不要に複雑な実装になっていないか
- 適切なテストが存在するか
- 後続の人間レビューを妨げる品質上の問題がないか

を確認する。

明確かつ安全に修正できる問題は修正し、実装をレビュー可能な状態へ整える。

仕様変更、プロダクト判断、大きなarchitecture changeはこのSkillでは行わない。

# 参照

レビュー開始前に、対象に応じて以下を確認する。

- `AGENTS.md`
- `.ai/policies/` の関連規則
- `docs/coding-guidelines.md`
- `docs/test-guidelines.md`
- 対象タスク
- 機能仕様
- `test-plan.md`
- `implementation.md`
- 実際のGit diff
- 変更後のソースコード
- 関連する既存実装とテスト

実装者の説明だけを根拠にせず、実際のコードを基準に判断する。

# 基本方針

## 変更箇所だけを孤立して評価しない

変更コードだけではなく、その周囲の既存コードと既存パターンを確認する。

特に以下を確認する。

- 同じ責務を持つ既存実装
- 既存の抽象化
- architecture boundary
- 命名・エラー処理・状態管理の既存パターン
- 同種のテスト

「一般的に良いコード」ではなく、**このリポジトリで一貫したコードになっているか**を重視する。

# 手順

## 1. タスクと変更範囲を確認する

対象タスクについて以下を確認する。

- 目標
- 対象範囲
- 対象外
- 受け入れ条件
- 必要な検証

Git diffと照合し、

- タスクと関係のない変更
- 想定外のファイル変更
- scope外の仕様変更
- 不要なリファクタリング

が含まれていないか確認する。

## 2. 既存設計との整合性を確認する

変更された各責務について、周辺コードと同種の既存実装を調査する。

以下を確認する。

- 既存の責務分割を維持しているか
- 既存の抽象化を再利用できているか
- 新しい抽象化が本当に必要か
- layer間の依存方向を守っているか
- domain logicが不適切なlayerへ漏れていないか
- UI / command / persistenceなどのarchitecture boundaryを守っているか

既存と異なる設計が採用されている場合は、その必要性を確認する。

単に異なるという理由だけで既存形式へ変更しない。

## 3. コーディングガイドラインをレビューする

`docs/coding-guidelines.md` と既存コードを基準に確認する。

特に以下を見る。

### 責務と構造

- 関数・クラス・モジュールの責務が明確か
- 意味のある処理単位が適切に切り出されているか
- 単に行数を減らすためだけの分割になっていないか
- 一つの関数へ複数の独立した責務を詰め込んでいないか
- 不要なwrapperや中間 abstractionを増やしていないか

### 命名

- 名前から役割や意図が分かるか
- boolean、状態、操作の命名が既存規則と整合しているか
- genericすぎる名前で意味を失っていないか

### コメント

コメントはコードの逐語的な説明ではなく、

- なぜこの実装なのか
- 外部制約
- 局所的にはわからない前提

など、コードだけでは分からない情報を説明しているか確認する。命名や関数分割で表現できる内容をコメントだけで補っている場合は、コード構造の改善を優先する。コメントについては特に重点的にガイドラインに従っているか確認する。

### 複雑性

- 不必要な条件分岐
- 重複処理
- premature abstraction
- 不要な状態
- 不要なmutable data
- 不自然な制御フロー

がないか確認する。

将来必要になるかもしれない、という理由だけの汎用化は避ける。

## 4. エラー処理と境界を確認する

変更箇所で発生し得る失敗について確認する。

- エラーを握りつぶしていないか
- 不正状態を正常系として扱っていないか
- validationの責務が適切な場所にあるか
- boundaryを跨ぐ際の型変換やvalidationが適切か
- domain errorとinfrastructure errorが不必要に混在していないか

既存のerror handling policyやパターンがある場合はそれに従う。

## 5. テストをレビューする

振る舞いを変更した箇所について、`docs/test-guidelines.md` と `test-plan.md` を基準に確認する。

以下を見る。

- 変更した振る舞いをテストしているか
- 実装詳細ではなく意味のある振る舞いを検証しているか
- happy pathだけで重要な境界条件を落としていないか
- 既存テストとの重複が過剰でないか
- mockが実装構造を固定しすぎていないか
- 不要に大きなintegration testでしか検証できない構造になっていないか

必要なテストが明確に不足している場合は追加または修正する。

## 6. 修正する

問題を次の2種類に分ける。

### その場で修正する

修正方法が明確で、仕様や設計判断を変えないもの。

例:

- ガイドラインに反した命名
- 明らかな不要コード
- 不要な重複
- 小さな責務分割の問題
- 不適切なコメント
- コメントの欠落
- formatter / lint違反
- 明確なarchitecture boundary違反で既存パターンへ戻せるもの
- 変更した振る舞いに対する明確なテスト不足

変更は問題を解消するための最小限に留める。

### 勝手に修正しない

複数の妥当な選択肢があり、人間の判断が必要なもの。

例:

- domain modelの責務変更
- public APIの変更
- architectureの変更
- 永続化方式の変更
- product behaviorの変更
- 仕様が曖昧なケース
- 大規模なリファクタリング

これらは問題と選択肢を報告し、勝手に決定しない。

## 7. 修正後に再確認する

修正を行った場合はdiffを再確認し、

- 新しいscope外変更を入れていないか
- 問題を別の場所へ移しただけになっていないか
- 既存設計との整合性を維持しているか
- 必要なテストが更新されているか

を確認する。

# レビュー観点

最終的に以下を確認する。

- [ ] タスクのscope内だけが変更されている
- [ ] 既存architecture boundaryを守っている
- [ ] 既存の抽象化・パターンを尊重している
- [ ] 不要な新規抽象化がない
- [ ] 関数・クラス・モジュールの責務が明確
- [ ] 命名から意図が読み取れる
- [ ] コメントがコードの逐語説明になっていない
- [ ] 不要な重複・複雑性・状態がない
- [ ] エラー処理とvalidationが適切
- [ ] 振る舞いの変更に対応するテストがある
- [ ] 関係のないリファクタリングがない
- [ ] プロジェクト標準の検証結果を確認した

# 出力

レビューと修正の結果を `.ai/features/<feature>/tasks/<task>/guideline-review.md` に記録する。

以下の形式を基本とする。

## 結果

`pass` / `fixed` / `needs-decision`

- `pass`: ガイドライン上の修正事項なし
- `fixed`: 明確な問題を修正済み
- `needs-decision`: 人間の設計・仕様判断が必要な問題が残っている

## 修正した内容

修正した場合だけ、何が問題で、どう修正したかを簡潔に記載する。

コードの逐語的な変更一覧にはしない。

## 残っている論点

人間の判断が必要なものだけ記載する。

各項目について、

- 問題
- 関連するガイドラインまたは設計
- なぜ自動修正しなかったか

を簡潔に示す。

問題がなければ省略する。

## 検証

実際に行った検証と結果を記録する。

未実施のものは未実施と明記する。

# ルール

- 実際のdiffとコードを確認してから評価する。
- 一般論よりリポジトリ固有のガイドラインと既存パターンを優先する。
- 問題を探すこと自体を目的にしない。
- ガイドラインに複数の解釈がある場合は断定しない。
- 正常なコードを好みのスタイルへ書き換えない。
- 関係のないリファクタリングを行わない。
- scope外の仕様変更を行わない。
- architecture changeを勝手に行わない。
- product判断を勝手に行わない。
- 修正する場合もタスク達成に必要な最小限のdiffを維持する。
- テストが通ることだけを理由に設計上の問題を無視しない。
- lintやformatが通ることだけをコード品質の根拠にしない。

# 完了条件

以下を満たした場合に完了とする。

- 対象変更をプロジェクトルールと既存実装に照らして確認した
- architecture / coding / test guidelineの主要な違反を確認した
- 明確かつ安全に修正可能な問題を修正した
- 修正後のdiffを再確認した
- 必要な検証を実行し、結果を記録した
- 自動修正できない設計・仕様上の論点を明示した
- 後続の実装レビューを開始できる状態になっている
