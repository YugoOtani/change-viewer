# 目的

実装済みの変更について、
Planとの差を評価する前に、

- プロジェクトルールに従っているか
- 既存アーキテクチャや抽象化を壊していないか
- 不要に複雑な実装になっていないか
- 適切なテストが存在するか
- テストが実装詳細を過度に固定していないか
- 後続の人間レビューを妨げる品質上の問題がないか

を確認する。

明確かつ安全に修正できる問題は修正し、
実装をレビュー可能な状態へ整える。

仕様変更、
プロダクト判断、
大きなarchitecture changeは
このSkillでは行わない。

# 参照

レビュー開始前に、
対象タスクの以下を確認する。

- `AGENTS.md`
- `.ai/policies/` の関連規則
- `docs/coding-guidelines.md`
- `docs/test-guidelines.md`
- `.ai/features/<feature-name>/tasks/<task-name>/task.md`
- `.ai/features/<feature-name>/tasks/<task-name>/plan-implementation.md`
- `.ai/features/<feature-name>/tasks/<task-name>/test-plan.md`
- `.ai/features/<feature-name>/tasks/<task-name>/implementation.md`
- 関連する機能仕様
- 実際のGit diff
- 変更後のソースコード
- 関連する既存実装とテスト

実装者の説明だけを根拠にせず、
実際のコードを基準に判断する。

# Planの扱い

`plan-implementation.md` は、
人間が実装前に確認した実装の骨格として参照する。

ただし、
このSkillの目的はPlanへの一致を強制することではない。

Planから実装が変わっていても、
実際の実装の方が自然でガイドラインに従っているなら、
Planへ戻すためだけの修正は行わない。

逆に、
Planどおりであっても
ガイドライン違反や不自然な設計があれば指摘する。

このSkillから
`plan-implementation.md` は変更しない。

# 基本方針

## 変更箇所だけを独立して評価しない

変更コードだけではなく、
その周囲の既存コードと既存パターンを確認する。

特に以下を確認する。

- 同じ責務を持つ既存実装
- 既存の抽象化
- architecture boundary
- 命名・エラー処理・状態管理の既存パターン
- 同種のテスト

「一般的に良いコード」ではなく、

**このリポジトリで一貫したコードになっているか**

を重視する。

# 手順

## 1. タスクと変更範囲を確認する

対象タスクについて以下を確認する。

- 目標
- 対象範囲
- 対象外
- 受け入れ条件
- 必要な検証

Git diffと照合し、

- タスクと関係のない変更
- 想定外のファイル変更
- scope外の仕様変更
- 不要なリファクタリング

が含まれていないか確認する。

Planにないという理由だけで
scope外とは判断しない。

タスクの目的と対象範囲を基準に判断する。

## 2. 既存設計との整合性を確認する

変更された各責務について、
周辺コードと同種の既存実装を調査する。

以下を確認する。

- 既存の責務分割を維持しているか
- 既存の抽象化を再利用できているか
- 新しい抽象化が本当に必要か
- layer間の依存方向を守っているか
- domain logicが不適切なlayerへ漏れていないか
- UI / command / persistenceなどのarchitecture boundaryを守っているか

既存と異なる設計が採用されている場合は、
その必要性を確認する。

単に異なるという理由だけで既存形式へ変更しない。

## 3. Public APIとObservable Behaviorを確認する

変更された主要な公開APIについて、

- クライアントから見た意味のある振る舞いを表しているか
- 1つの振る舞いを不自然に複数APIへ分割していないか
- observable behaviorと公開境界が大きくずれていないか
- テストのためだけの公開APIを追加していないか

を確認する。

単体テストのActが
複数の公開API呼び出しを必要としている場合は、

単純にテストだけを修正せず、

**production APIの責務に問題がないか**

を検討する。

複数の設計が妥当な場合は
`needs-decision` として残す。

## 4. Domain LogicとControllerの分離を確認する

複雑なbusiness logicについて、

- immutableな入力から結果を求めるdomain logic
- mutableな共有依存を扱うcontroller

へ自然に分離されているか確認する。

以下の組み合わせは特に注意する。

```text
複雑なbusiness logic
+
DB / filesystem / network等のmutable dependency
```

同じ責務に混在している場合は、
分離できないか検討する。

Domain Logicは、
可能な限り出力値ベーステストで検証できる構造になっているか確認する。

ただし、
テストしやすさだけのために不要な層を追加しない。

## 5. コーディングガイドラインをレビューする

`docs/coding-guidelines.md` と既存コードを基準に確認する。

### 責務と構造

- 関数・クラス・モジュールの責務が明確か
- 意味のある処理単位が適切に切り出されているか
- 単に行数を減らすためだけの分割になっていないか
- 一つの関数へ複数の独立した責務を詰め込んでいないか
- 不要なwrapperや中間abstractionを増やしていないか

### 命名

- 名前から役割や意図が分かるか
- boolean、状態、操作の命名が既存規則と整合しているか
- genericすぎる名前で意味を失っていないか

### コメント

関数、処理単位、データ型には、
プロジェクトのガイドラインに従って必要なコメントがあるか確認する。

コメントは、

- コードから読み取りにくい意図
- 外部制約
- 局所的には分からない前提

などを説明しているか確認する。

命名や関数分割で表現できる内容を
コメントだけで補っている場合は、
コード構造の改善を優先する。

コメントは自然な日本語で記述する。

### 複雑性

以下が不必要に増えていないか確認する。

- 条件分岐
- 重複処理
- premature abstraction
- 状態
- mutable data
- 不自然な制御フロー

将来必要になるかもしれないという理由だけの汎用化は避ける。

## 6. エラー処理と境界を確認する

変更箇所で発生し得る失敗について確認する。

- エラーを握りつぶしていないか
- 不正状態を正常系として扱っていないか
- validationの責務が適切な場所にあるか
- boundaryを跨ぐ際の型変換やvalidationが適切か
- domain errorとinfrastructure errorが不必要に混在していないか

既存のerror handling policyやパターンがある場合はそれに従う。

## 7. テスト構造をレビューする

振る舞いを変更した箇所について、
`docs/test-guidelines.md` と `test-plan.md` を基準に確認する。

### Arrange / Act / Assert

- Arrange → Act → Assertの順になっているか
- 各フェーズが原則1回ずつになっているか
- 通常は空行で区切られているか
- フェーズ内部にも空行が必要な場合だけAAAコメントを使っているか

### 1テスト1振る舞い

- 独立した複数の振る舞いを1つのテストで検証していないか
- 同じsetupというだけで無関係なassertionをまとめていないか

### Act

- 原則として1つの公開API操作になっているか
- helperで複数の公開操作を隠して1行に見せかけていないか

Actが不自然に複数APIになっている場合は、
production API設計上の問題も検討する。

### Assert

- observable resultを検証しているか
- private stateや中間状態を過剰に検証していないか
- 実装手順を固定するassertionになっていないか

### 命名

- HowではなくWhatが書かれているか
- 内部method名や呼び出し回数を中心とした名前になっていないか

### パラメータ化

同一振る舞いについて
入力値だけを変えた重複テストがある場合は、
parameterized testを検討する。

## 8. Mock / Stubをレビューする

Test Doubleについて役割を確認する。

### Stub

入力を供給するためのStubについて、

- 呼び出し回数
- 呼び出し順
- 呼び出したmethod

を検証していないか確認する。

Stubとのinteractionは実装詳細として扱う。

### Mock

外部へのobservable interactionを検証するためのMockだけを許容する。

内部コンポーネント間の呼び出しを
Mockで過度に固定していないか確認する。

## 9. 出力値ベーステストを確認する

複雑なdomain logicについては、

```text
input
 ↓
domain logic
 ↓
output
```

という出力値ベーステストを優先できているか確認する。

以下へ不必要に依存している場合は見直す。

- 内部状態
- collaborator interaction
- 実行手順
- private method

出力値だけで十分振る舞いを確認できる場合は、
interaction-basedなテストを追加しない。

## 10. テストレベルを確認する

- 単体テストで十分なものを不要にE2Eへ上げていないか
- integration contractが必要なのにMockだけで済ませていないか
- 退行への耐性とfeedback速度のバランスが不自然でないか

を確認する。

## 11. 修正する

問題を次の2種類に分ける。

### その場で修正する

修正方法が明確で、
仕様や主要な設計判断を変えないもの。

例:

- AAAの構造崩れ
- Howを含むテスト名
- Stub interactionの不要なassert
- 同一振る舞いの明らかな重複テスト
- ガイドラインに反した命名
- 明らかな不要コード
- formatter / lint違反
- 明確なテスト不足

変更は問題を解消するための最小限に留める。

### 勝手に修正しない

複数の妥当な選択肢があり、
人間の判断が必要なもの。

例:

- public APIの再設計
- domain / controller境界の変更
- architectureの変更
- domain modelの責務変更
- 永続化方式の変更
- product behaviorの変更
- 大規模なリファクタリング

特に、

**Actを1つのAPIにするためのproduction API変更**

は、
自動的に行わない。

設計上の論点として残す。

## 12. 修正後に再確認する

修正を行った場合はdiffを再確認し、

- 新しいscope外変更を入れていないか
- 問題を別の場所へ移しただけになっていないか
- 既存設計との整合性を維持しているか
- 必要なテストが更新されているか

を確認する。

Planとの差異を隠す目的で
`plan-implementation.md` を変更しない。

# レビュー観点

- [ ] タスクのscope内だけが変更されている
- [ ] 既存architecture boundaryを守っている
- [ ] 既存の抽象化・パターンを尊重している
- [ ] 不要な新規抽象化がない
- [ ] 関数・クラス・モジュールの責務が明確
- [ ] observable behaviorとpublic APIが大きくずれていない
- [ ] 複雑なdomain logicとmutable dependencyが不自然に混在していない
- [ ] 命名から意図が読み取れる
- [ ] コメントがコードの逐語説明になっていない
- [ ] 不要な重複・複雑性・状態がない
- [ ] エラー処理とvalidationが適切
- [ ] 振る舞いの変更に対応するテストがある
- [ ] テストがArrange → Act → Assertになっている
- [ ] 1テスト1振る舞いになっている
- [ ] Actが原則として1つの公開操作になっている
- [ ] テスト名がWhatを表している
- [ ] observable resultを検証している
- [ ] Stubとのinteractionを検証していない
- [ ] Mockが外部へのobservable interactionに限定されている
- [ ] domain logicで出力値ベーステストを優先している
- [ ] 関係のないリファクタリングがない
- [ ] プロジェクト標準の検証結果を確認した

# 出力

レビューと修正の結果は必ず以下へ記録する。

`.ai/features/<feature-name>/tasks/<task-name>/guideline-review.md`

基本形式:

```md
# ガイドラインレビュー

## 結果

`pass` / `fixed` / `needs-decision`

## 修正した内容

修正した場合のみ記載する。

## 残っている論点

人間の判断が必要な場合のみ記載する。

## 検証

実際に行った検証と結果を記載する。
未実施のものは未実施と明記する。
```

結果の意味:

- `pass`: ガイドライン上の修正事項なし
- `fixed`: 明確な問題を修正済み
- `needs-decision`: 人間の設計・仕様判断が必要な問題が残っている

# ルール

- 実際のdiffとコードを確認してから評価する
- 一般論よりリポジトリ固有のガイドラインと既存パターンを優先する
- 問題を探すこと自体を目的にしない
- ガイドラインに複数の解釈がある場合は断定しない
- 正常なコードを好みのスタイルへ書き換えない
- 関係のないリファクタリングを行わない
- scope外の仕様変更を行わない
- architecture changeを勝手に行わない
- product判断を勝手に行わない
- テスト都合だけでproduction APIを変更しない
- Planへの一致を目的にコードを修正しない
- `plan-implementation.md` をActualに合わせて変更しない
