# 目的

曖昧な要求を、実装計画を立てられる程度に明確な仕様へ変換する。

このSkillでは実装を行わない。

実装方法を先に決めるのではなく、

- 何を解決したいのか
- ユーザーから見て何が起きるべきか
- 何をもって完成とするのか

を明確にする。

# 手順

## 1. 要求を理解する

以下を整理する。

- ユーザーが達成したいこと
- 解決したい問題
- この機能が必要な理由
- ユーザーから見える振る舞い
- 既存ワークフローへの影響
- 既存機能で変更される可能性があるもの

必要に応じて、既存コード・ドキュメント・仕様を確認する。

ユーザーが提示した「解決方法」と、本来達成したい「目的」を区別する。

例えば、

「ボタンを追加したい」

という要求の場合、

ボタンそのものではなく、

「ユーザーが何を行えるようになりたいのか」

を確認する。

## 2. 不明点を分類する

不明点を以下に分類する。

### プロダクト上の意思決定

ユーザーから見える挙動や体験に影響するもの。

例:

- いつ表示するか
- 自動で行うか手動で行うか
- エラー時にどう振る舞うか

### 技術的制約

既存アーキテクチャ、プラットフォーム、互換性などによって決まるもの。

### 実装時に決めてよい詳細

ユーザー体験に大きな影響を与えず、
既存の開発規約から合理的に決められるもの。

人間の判断が不要な詳細について、
不要な質問を増やさないこと。

## 3. 重要な意思決定を提示する

未確定のプロダクト上の判断が重要な場合は、
少数の意味のある選択肢を提示する。

各選択肢について以下を説明する。

- どのように振る舞うか
- 利点
- 欠点
- 他の機能や将来への影響

既存の仕様やプロジェクト方針から明らかに決まるものについて、
人工的な選択肢を作らない。

## 4. 仕様を作成する

以下のファイルを作成または更新する。

`.ai/features/<feature-name>/spec.md`
テンプレートには`.ai/templates/spec.md`を使用する。


# ルール

- 原則として実装方法には踏み込まない。
- 技術的制約上必要な場合のみ、技術的な内容を仕様へ含める。
- 仕様を完成させるためだけに存在しない要件を追加しない。
- 確定事項と仮定を区別する。
- 内部実装ではなく観測可能な振る舞いを優先する。
- 受け入れ条件は検証可能でなければならない。
- このSkillでは実装計画を作らない。
- このSkillではコードを変更しない。
